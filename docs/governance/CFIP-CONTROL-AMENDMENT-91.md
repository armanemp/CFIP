# CFIP Control Amendment 91 — Structural Hygiene + Intelligence Runtime

**Status:** ACTIVE  
**Scope:** controlled Gate-0 implementation and repository/documentation reconciliation  
**Supersedes:** stale structural assumptions that equate source engine census with target directory materialization; stale Gate-0 wording that categorically prohibited controlled implementation.

## 1. Structural truth

The target repository must represent actual ownership, not a visual copy of the source tree.

- Empty or README-only directories are not implementation evidence.
- A target namespace may remain when it is an explicit architecture/ownership contract or contains executable implementation.
- Unused placeholder engine namespaces and redundant compatibility facades must be removed after reference analysis.
- Historical/source inventories remain evidence records and must not be mistaken for physical target implementations.
- One physical numerical owner is required per canonical technical-indicator family.
- Repository structure validators must fail when obsolete technical facades or duplicate calculation surfaces return.

## 2. Gate-0 implementation semantics

Gate 0 is OPEN for controlled implementation. A controlled slice must be source-evidenced or explicitly justified as a target addition, contract-first, reversible, testable, observable, tied to an ECP/change identity, and kept behind applicable runtime/promotion gates.

Controlled implementation is not parity proof and never unlocks production promotion, live trading or irreversible high-impact behavior.

## 3. Technical indicator progression

The canonical technical engine may continue expanding its implementation while parity remains explicitly unverified. New indicators must:

1. have one physical canonical owner;
2. preserve explicit warm-up/missingness;
3. validate finite/ordered inputs and parameter bounds;
4. be registered by stable `(indicator_id, version)` metadata;
5. have deterministic tests;
6. avoid duplicate calculation in evidence/consensus layers;
7. remain source-parity-unverified until source-specific formulas/defaults and golden fixtures close the gap.

Current controlled target catalog includes 24 registered indicator families/output sets, including DEMA, TEMA, TRIX and Parabolic SAR.

## 4. Unified analysis boundary

`AnalysisConsensusService` remains the sole directional aggregation authority. Technical outputs are translated through `IndicatorEvidenceAdapter`; unsupported semantic mappings fail closed. Consensus results now include deterministic conflict classification and a compact explanation trace so UI/API/runtime consumers do not need to recreate aggregation semantics.

Consensus remains revision-bound and abstains on insufficient confidence/margin or lack of directional evidence.

## 5. Platform Intelligence runtime foundation

`packages/intelligence-runtime` is a dependency-free cross-cutting lifecycle contract for:

`observe → context → reason → act → verify → learn → audit → safety`

It records immutable, policy-bound lifecycle events and requires an explicit prior safety event before recording an `act` stage. It does not execute SQL, infrastructure mutation, trades or arbitrary agent actions. Domain services and governed application tools remain authoritative.

## 6. Verification requirements

Fresh current-head CI is required before any new slice is marked Verified. Previous successful workflow runs may be reported only against their exact tested commit. Parity, scale, production readiness and live-runtime safety remain OPEN until executable evidence closes them.

## 7. Documentation requirements

The target manifest, Gate-0 register, continuation pointer and progress report must agree on:

- physical engine tree;
- controlled implementation semantics;
- technical indicator ownership;
- Platform Intelligence runtime boundary;
- Applied vs Verified vs Open status.

Historical reports are not rewritten merely to erase history, but stale canonical/current-state documents must be reconciled.
