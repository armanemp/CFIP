The API then constructs `AnalysisFabric(_engine_runtime)` from this runtime and exposes the runtime engine IDs and health through `/v1/trading/analysis/engines`.

### 2.2 Same-timeline execution path

`/v1/trading/analysis/engine-evidence`:

1. validates requested bar count;
2. obtains a causal workspace snapshot;
3. converts the same snapshot into the engine observation tuple;
4. propagates the snapshot `data_revision`;
5. propagates the snapshot `as_of`;
6. generates a correlation ID;
7. executes the registered runtime engine IDs through `AnalysisFabric`;
8. returns engine outputs and derived evidence.

This is direct evidence that the runtime is designed around a shared causal input timeline rather than each engine independently loading market state.

### 2.3 Production engine contracts

Directly verified `fi_contracts.analysis.engine`:

- `EngineDescriptorV2`
- `EngineExecutionContext`
- `EngineEvidence`
- `EngineOutput`
- `EngineHealthSnapshot`

V2 explicitly carries timeframes, dependencies, warmup bars, latency budget, failure policy, deterministic flag and capability ID. Execution context carries instrument, timeframe, data revision, observations and as-of time. Output carries bounded direction/score/confidence, evidence/provenance and degraded status. Health tracks executions, failures, timeouts, latency, failure rate and score.

The historical `fi_contracts.analysis.execution` contract separately provides input/parameter/engine hashes and dependency-version provenance. This creates an important V1/V2 reconciliation task rather than evidence for silently choosing one.

### 2.4 Runtime/API observability

Engine registration is observable through the API rather than remaining hidden construction state. The engine catalog route returns each runtime descriptor plus current health. The engine-evidence route exposes output/evidence generated by the same runtime registry.

### 2.5 Negative evidence preserved

The `technical` namespace is explicitly preserved as a reference/passthrough implementation, not a complete technical-indicator engine. CFIP must not claim technical-indicator parity from the namespace alone.
